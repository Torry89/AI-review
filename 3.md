### Пример 2
Ситуация: обработчик принимает параметр status и собирает SQL строкой

package handlers
import (
“database/sql”
“fmt”
“net/http”
)

func Orders(db *sql.DB, w http.ResponseWriter, r *http.Request) error {
status := r.URL.Query().Get(“status”)
query := fmt.Sprintf(“SELECT id, total FROM orders WHERE status = ‘%s’”, status)
_, err := db.Query(query)
return err
}
***Промт:***
> Ты код-ревьер, 
```
package handlers
import (
“database/sql”
“fmt”
“net/http”
)

func Orders(db *sql.DB, w http.ResponseWriter, r *http.Request) error {
status := r.URL.Query().Get(“status”)
query := fmt.Sprintf(“SELECT id, total FROM orders WHERE status = ‘%s’”, status)
_, err := db.Query(query)
return err
}
```
> Твоя задача проверить код на ошибки, наличие уязимостей и т.д.
Не предлагай рефакторинг без причины.
Формат ответа:
> - blocker/major/minor
> - что не так, риск(высокий/средний/низкий), как исправить

***Ответ ИИ:***
blocker — SQL-инъекция: status из r.URL.Query().Get("status") подставляется в SQL через fmt.Sprintf. 
Риск: высокий — выполнение произвольного SQL, чтение/изменение/удаление данных.  
Исправить: параметризованный запрос, например db.QueryContext(r.Context(), "SELECT id, total FROM orders WHERE status = $1", status) (для MySQL — ?), fmt.Sprintf убрать.  

blocker (если кавычки в коде реальные) — импорты указаны «умными» кавычками “database/sql”. 
Риск: высокий — код не скомпилируется.
Исправить на обычные "database/sql", "fmt", "net/http".

major — db.Query возвращает *sql.Rows, но результат отбрасывается: _, err := db.Query(query). rows.Close() не вызывается.  
Риск: высокий — утечка соединений/ресурсов и исчерпание пула БД под нагрузкой.  
Исправить: сохранить rows, сделать defer rows.Close(), проверять rows.Err(); если нужна одна строка — QueryRowContext.

major/условно — handler не пишет HTTP-ответ: w не используется, нет WriteHeader/тела/обработки ошибки на уровне HTTP.  
Риск: средний — если внешний middleware не обрабатывает возвращённую ошибку, клиент получит пустой ответ/200.  
Исправить: явно писать статус и тело либо полагаться на документированный middleware.

minor — нет проверки HTTP-метода.  
Риск: низкий — handler может обработать неожиданный метод.   
Исправить: ограничить метод, если ожидается GET.

minor — нет использования контекста запроса.   
Риск: низкий/средний — запрос к БД не отменяется при отмене HTTP-запроса.   
Исправить: использовать QueryContext(r.Context(), ...).

minor — fmt нужен только из-за небезопасного Sprintf; после перехода на параметры его можно убрать.  
Риск: низкий — лишняя зависимость/поддержка небезопасного паттерна.

## PR
1.  SQL-инъекция
   Что не так: status из r.URL.Query().Get("status") подставляется в SQL через fmt.Sprintf:
```go
query := fmt.Sprintf("SELECT id, total FROM orders WHERE status = '%s'", status)
```
Риск: высокий — выполнение произвольного SQL, чтение/изменение/удаление данных.  
Как исправить: параметризованный запрос, fmt.Sprintf убрать:
```go
rows, err := db.QueryContext(r.Context(),
"SELECT id, total FROM orders WHERE status = $1", status) // для MySQL — "?"
```
Приоритет: blocker

2. Утечка *sql.Rows

Что не так: результат db.Query(query) отбрасывается (_), rows.Close() не вызывается.  
Риск: высокий — исчерпание пула соединений под нагрузкой.  
Как исправить: сохранить rows, defer rows.Close(), обрабатывать rows.Err(); для одной строки — QueryRowContext.  
Приоритет: major

3. Нет контекста запроса

Что не так: запрос к БД не отменяется при отмене HTTP-запроса.  
Риск: средний — «висящие» запросы к БД при отмене клиента/таймауте.  
Как исправить: перейти на QueryContext(r.Context(), ...); проверить тестами, что поведение по таймаутам/отмене ожидаемое.  
Приоритет: minor

4. Лишний импорт fmt

Что не так: fmt нужен только ради небезопасного Sprintf.  
Риск: низкий — лишняя зависимость, поддержка небезопасного паттерна.  
Как исправить: удалить импорт после исправления проблемы 1; проверить go build/go vet.  
Приоритет: minor

5. Нет явной записи HTTP-ответа (w не используется; WriteHeader/тело отсутствуют).   

Риск: средний, если внешний middleware не превращает возвращённый error в HTTP-статус.
Приоритет: major/verify — проверить регистрацию handler’ов и наличие middleware; тестами зафиксировать фактический ответ клиенту.

6. Нет проверки HTTP-метода.

Риск: низкий, если метод не ограничен роутером.  
Приоритет: minor/verify — проверить роутинг; при необходимости добавить проверку и тест на 405.

7. «Умные» кавычки в импортах snippet’а (“database/sql”).
Риск: высокий (не соберётся), если в реальном файле кавычки такие. 
Приоритет: blocker/verify — открыть исходник и подтвердить; при подтверждении заменить на ".
